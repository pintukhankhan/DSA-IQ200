Linked Lists — reason about pointers.

A linked list trades direct indexing for flexible links. The deep skill is tracking references: who points to whom, which node is reachable from head, and what must change when a link is rewritten.

IQ 200 MODEL

Pointer invariant

head → node → node → … → null
10× question: If you delete node B from A → B → C, what single link must change?
A.next must be changed from B to C. B becomes unreachable from head unless another reference still points to it.

Insertion after a known node

Given node A and a new node X, insertion between A and B is constant time: save B, set X.next = B, then A.next = X. The trick is that finding A may still cost O(n). Complexity must include the search cost when A is not already known.

// A → B becomes A → X → B
X.next = A.next
A.next = X

Deletion after a known predecessor

For a singly linked list, deleting B is easy once A is known: A.next = B.next. But if only B is given, there is no previous pointer to update. That distinction is a classic interview trap.

Trap: “Linked-list deletion is O(1)” is incomplete. It is O(1) given the required predecessor/reference.

Why no O(1) indexing?

Node 17 is not found by arithmetic. You must follow links from head (or another known node). Therefore index lookup is O(n) in a normal singly linked list.

Doubly linked list

Each node has next and prev. This supports backward traversal and easier local deletion when the node itself is known, at the cost of extra memory and more pointer updates.

Memory locality

Nodes may be scattered in memory. Pointer chasing can cause cache misses, so a theoretically elegant linked list can be slower than an array in practice.

REVERSAL PROOF

Reverse a singly linked list without losing the chain

Maintain three references: prev, cur, and next. Before changing cur.next, save the original next node. Then point cur backward and advance. The invariant is: prev is the reversed prefix, cur is the first unprocessed node, and no unprocessed node becomes unreachable.

prev = null
cur = head

while cur != null:
  next = cur.next // save chain
  cur.next = prev // reverse link
  prev = cur
  cur = next

head = prev
SOCRATIC CHECK

Can you prove the operation?

What happens if head is null? What happens for one node? What happens if the list contains a cycle? Why does Floyd's slow-and-fast pointer method detect a cycle?

Empty list: cur is null, so the loop does nothing and head becomes null.

One node: its next becomes null and it becomes the new head.

Cycle: slow moves one edge and fast two. If a cycle exists, the faster pointer eventually laps the slower one and they meet.
